# Owner Override — Ambiguous Reason & Participant Name Correction — Design

**Date:** 2026-10-08
**Author:** Claude (brainstorming session with Nishant)
**Status:** Approved for planning

## Goal

The manual owner-override feature (`GET`/`POST /api/owner-overrides`) currently
gives a human resolving an ambiguous conversation almost nothing to work
with: a `conversationKey`, a possibly-null `participantName`, and a
timestamp. It never says *why* HubSpot's name-match resolver couldn't pick
an owner, so the human can't tell whether they're looking at "no name was
ever captured," "two different HubSpot contacts share this name," or
something else — each of which calls for a different action.

This feature:
1. Records *why* a conversation is `'ambiguous'` at resolution time, and
   surfaces that reason in the override-listing API.
2. Adds a LinkedIn-thread link (`conversationUrl`) to the listing so a human
   can identify the contact even when no name was ever captured.
3. Lets the human attach/correct a participant name as part of resolving an
   override — including deliberately renaming to a disambiguating label
   (e.g. `"contact_a" → "contact_a_b"`) when two real people share an exact
   name — with full before/after history kept in the audit trail.
4. Requires the targeted conversation to actually be in an unresolved state
   before an override can be applied, closing a previously-accepted gap.

## Non-Goals

- **No backfill for already-ambiguous conversations.** The ~17 conversations
  already sitting in `conversation_owner_cache` with `attribution_source =
  'ambiguous'` before this ships will show `ambiguousReason: null` forever —
  recorded by the old code before this feature existed, never
  retroactively corrected. New ambiguous conversations, resolved by this
  updated code, always get a reason. Not a defect, an accepted limitation
  (see "Open Questions / Accepted Gaps").
- **No cross-conversation name→owner memory.** A manual override is sticky
  only for the specific `conversationKey` it was applied to (via the
  existing unconditional cache short-circuit). A brand-new conversation with
  the same person — which would have a different `conversationKey`, since
  LinkedIn thread IDs aren't generated by this scraper — is NOT covered by a
  prior override and goes through the resolver fresh. Confirmed acceptable:
  this is the uncommon case (LinkedIn reuses the same thread for an ongoing
  1:1 relationship); per-conversation stickiness is what's being built.
- **No structural validation of the entered name.** `participantName` is
  free text — it may be a real corrected name or a disambiguation label with
  no resemblance to an actual person's name (e.g. `"contact_a_b"`). The API
  only requires it be non-blank when the field is present at all.
- **No frontend confirmation UI.** The backend always applies an overwrite
  when `participantName` is provided — any "are you sure you want to
  replace an existing name?" UX is the frontend's responsibility, not this
  API's.

## Architecture

### Schema changes (new migration)

**`conversation_owner_cache`** gains one nullable column:
- `ambiguous_reason TEXT` — one of the 5 reason codes below, set whenever
  the resolver lands on `'ambiguous'`; cleared to `NULL` when a row
  transitions to `'manual'` via an override. `NULL` on any non-ambiguous
  row, and permanently `NULL` on pre-existing ambiguous rows this feature
  never re-evaluates.

**`owner_override_audit`** gains three nullable columns:
- `ambiguous_reason TEXT` — a **snapshot** of the reason that was on the
  conversation immediately before this override (history, not live state;
  distinct from the live column above, which gets cleared).
- `old_participant_name TEXT` — the participant name in effect before this
  override (cross-scraper lookup — see below), regardless of whether this
  override changed it.
- `new_participant_name TEXT` — the name provided in this override's
  request body, or `NULL` if no name was provided (meaning "no name change
  was attempted in this override," distinguishable from "the name was
  unchanged because the provided value matched the old one").

Plain `TEXT` columns, no DB-level enum, matching every other
attribution-adjacent column in this schema (`attribution_source` itself is
plain `TEXT`).

### The 5 ambiguous-reason codes

Derived directly from `MessageOwnerResolverService.resolveOwnerFromHubSpot`'s
existing branches — this change makes each branch report which one it took,
it does not add new resolution logic:

| Code | Current resolver condition |
|---|---|
| `NO_NAME` | `participantName` was never captured (`!name`) — HubSpot is never called. |
| `SINGLE_WORD_NAME` | A name was captured but has no space (empty last name) — `findContactOwnerIdByName` short-circuits before calling HubSpot. |
| `NO_HUBSPOT_MATCH` | A real first+last name was searched; 0 HubSpot contacts matched exactly. |
| `MULTIPLE_HUBSPOT_MATCHES` | The first+last name matched 2+ HubSpot contacts (the collision case this feature is largely motivated by). |
| `OWNER_NOT_CONNECTED` | Exactly 1 HubSpot contact matched, but its assigned HubSpot owner isn't a connected Techeniac user. |

Note: `NO_HUBSPOT_MATCH` and `MULTIPLE_HUBSPOT_MATCHES` currently collapse
into one branch in the resolver (`matchCount !== 1`) — this change splits
that branch's return value on `matchCount === 0` vs `matchCount >= 2` to
report the correct code, without altering the actual resolution behavior
(both still result in `'ambiguous'`, nothing about *when* a conversation
goes ambiguous changes).

### Code changes by file

- `src/services/messageOwnerResolverService.ts` — `resolveOwnerFromHubSpot`'s
  return type gains an `ambiguousReason?: AmbiguousReason` field, populated
  on every branch that returns `source: "ambiguous"`. `resolveAndPersist`
  passes it through to the cache upsert.
- `src/repositories/conversationOwnerCacheRepository.ts` — `upsert` gains an
  optional `ambiguousReason` param, written to the new column (and cleared
  to `NULL` whenever the source isn't `'ambiguous'` — i.e. the override
  path already clears it naturally by passing nothing/undefined).
- `src/repositories/ownerOverrideRepository.ts`:
  - `listAmbiguous` query gains `c.ambiguous_reason AS "ambiguousReason"` in
    its `SELECT`.
  - A new method to fetch the current cross-scraper participant name and
    current `ambiguous_reason` for a single `conversationKey` (needed as the
    "old" snapshot before an override — reuses the same cross-scraper
    `message_activity` lookup technique already used by the resolver's own
    `I2` fix and the listing query's `LATERAL` join).
  - `applyOverride` gains `participantName?: string`, `ambiguousReason:
    string | null` (snapshot), `oldParticipantName: string | null` params;
    adds a `message_activity.updateMany` (uniform across every scraper row
    for that `conversationKey`) when `participantName` is provided, and
    passes the audit columns through — all still inside the single
    `prisma.$transaction`.
- `src/services/ownerOverrideService.ts`:
  - `applyOverride` gains a **new required check**: look up the
    conversation's current `attribution_source`; if it isn't `'ambiguous'`,
    throw a new `ConflictError` (409) before doing anything else — closes
    the previously-accepted gap where any conversation could be overridden
    regardless of state.
  - Validates `participantName` if the field is present: must be non-blank
    after trimming, else `ValidationError` (400). Absent field = no name
    change attempted (not an error).
  - Fetches the "old" snapshot (reason + participant name) before calling
    the repository's transactional write.
- `src/controllers/ownerOverrideController.ts`:
  - `listOwnerOverrides` response rows gain `ambiguousReason` and
    `conversationUrl` fields. `conversationUrl` reuses the same
    slug-extraction *technique* as `publicController.ts`'s
    `conversationUrlFromKey` (a fresh, local copy — that existing helper is
    in active use by 3 unrelated report endpoints and must not be touched
    or imported cross-module for this).
  - `applyOwnerOverride` parses the optional `participantName` from
    `req.body` and passes it through.
- `src/errors/AppError.ts` — add `ConflictError extends AppError` (409).
  Confirmed absent: only `ValidationError`/`UnauthorizedError`/
  `ForbiddenError` currently exist in this file.

## API Changes

### `GET /api/owner-overrides`

Each row in `data.data[]` gains:
```json
{
  "conversationKey": "...",
  "participantName": "Maarten Kling",
  "resolvedAt": "...",
  "ambiguousReason": "MULTIPLE_HUBSPOT_MATCHES",
  "conversationUrl": "https://www.linkedin.com/messaging/thread/<slug>/"
}
```
`ambiguousReason` is `null` for pre-existing rows this feature doesn't
retroactively label (see Non-Goals). `conversationUrl` is `null` if the
`conversationKey` doesn't contain a recognizable LinkedIn thread slug
(defensive — mirrors the existing helper's own null-fallback behavior).

Pagination/search/sort (added in PR #30) are unaffected by this change.

### `POST /api/owner-overrides/:conversationKey`

Body gains an optional field:
```json
{ "ownerId": "<User.id>", "participantName": "contact_a_b" }
```

New behavior:
- **409 Conflict** if the targeted conversation's current
  `attribution_source` isn't `'ambiguous'` — "Conversation is not in a
  resolvable state." (New validation; previously any conversation could be
  overridden regardless of state.)
- **400 ValidationError** if `participantName` is present in the body but
  blank/whitespace-only after trimming.
- If `participantName` is present and non-blank: **always overwrites**
  every `message_activity` row for that `conversationKey` (uniform across
  scrapers) — no "already set, refusing" check. The frontend is responsible
  for any "are you sure?" confirmation before sending this field.
- If `participantName` is absent: no name change attempted; the audit row's
  `new_participant_name` is `NULL`.
- Response shape unchanged: `{ conversationKey, ownerId }`.

Every override, regardless of whether `participantName` was sent, writes
one `owner_override_audit` row with `ambiguous_reason` (the pre-override
snapshot), `old_participant_name`, and `new_participant_name` populated per
the rules above, alongside the existing `oldOwnerId`/`newOwnerId`/
`performedByEmail`/`performedAt`.

## Error Handling & Edge Cases

- **Blank `participantName`** (empty string or whitespace-only) when the
  field is present → `400 ValidationError`, not a silent no-op. Omitting
  the field entirely is the only way to signal "no name change."
- **Overriding a non-ambiguous conversation** → `409 Conflict`, new
  behavior (previously silently allowed).
- **Pre-existing ambiguous rows** (resolved by the old code, before this
  ships) → `ambiguousReason: null` permanently; accepted, not fixed here.
  All newly-ambiguous conversations from this point forward get a real
  reason.

## Testing

No mocking library in this repository (confirmed during the original
owner-attribution plan); verification continues to be manual against the
real dev DB, same pattern as every other task in that original plan:
1. Trigger each of the 5 ambiguous branches (seed/observe real
   conversations) and confirm the correct `ambiguousReason` lands in
   `conversation_owner_cache`.
2. Apply an override with `participantName` provided — confirm every
   `message_activity` row for that `conversationKey` updates uniformly, and
   the audit row's `old_participant_name`/`new_participant_name` are
   correct.
3. Apply an override without `participantName` — confirm no name change,
   `new_participant_name` is `NULL` in the audit row.
4. Attempt an override on a non-ambiguous conversation — confirm `409`.
5. Attempt an override with a blank `participantName` — confirm `400`.
6. Confirm `GET /api/owner-overrides` returns the right `ambiguousReason`
   and a correctly-formed `conversationUrl` for a conversation with a
   LinkedIn-thread-shaped `conversationKey`.

## Open Questions / Accepted Gaps

- No backfill for the ~17 pre-existing ambiguous conversations' reason —
  explicitly accepted as a gap by the person requesting this feature.
